Справка: правила проверки работоспособности (health check) в современной версии Docker, которые нужно учитывать:
- у инструкции HEALTHCHECK в Dockerfile есть параметры --interval, --timeout, --retries и --start-period — это те же настройки, что поля interval, timeout, retries и start_period секции healthcheck в Compose (с. 132). Значения по умолчанию: interval 30s, timeout 30s,
  retries 3, start-period 0s;
- если start_period (--start-period) не задан, первая проверка выполняется через interval после запуска контейнера; до первого результата у контейнера статус (health: starting);
- в книге (с. 132) start_period описан как время ожидания перед проверками. Точнее (документация Docker): в этот период проверки уже выполняются, но неудачные проверки не засчитываются в retries; если проверка в этот период прошла успешно, контейнер сразу получает статус (healthy);
- в выводе docker container ls статус выглядит так:
  Up 2 minutes (healthy), Up 2 minutes (unhealthy).

Справка — правила Docker 29 / Docker Compose v5, которых нет в главе 8 или которые в книге описаны иначе:
  1. Проверка (health check) выполняется внутри контейнера: первая — через interval после запуска контейнера, следующие — каждые interval (длительность самой проверки не учитывайте; в заданиях события не совпадают с моментами проверок). Код выхода (exit code) 0 — успех, любой другой — неудача.
  2. До первого результата статус — (health: starting). Успешная проверка сразу даёт (healthy) и обнуляет счётчик неудач подряд (FailingStreak). Когда счётчик достигает retries, статус — (unhealthy). Проверки продолжаются и в состоянии unhealthy.
  3. start_period: пока статус (health: starting) и время от запуска меньше start_period, неудачные проверки не засчитываются в счётчик (в книге на с. 132 сказано, что проверки в этот период не запускаются, — на деле запускаются). После первой успешной проверки неудачи засчитываются всегда, даже если start_period ещё не истёк.
  4. restart: on-failure — Docker перезапускает контейнер, если его процесс завершился с ненулевым кодом. Паузы между попытками растут (0,1 с, 0,2 с, 0,4 с, …), но не больше 1 минуты; во время паузы docker container ls показывает Restarting (1).
  5. Длинная форма depends_on:
       depends_on:
         api:
           condition: service_healthy
     service_started — зависимый сервис запускается после запуска зависимости (как короткая форма); service_healthy — после того, как зависимость стала (healthy). Compose сначала создаёт все контейнеры (Created), затем запускает их в порядке зависимостей. Если зависимость стала (unhealthy) раньше, чем (healthy), команда up завершается с ошибкой «dependency failed to start».

Справка (правила Docker, которые нужны для ответа):
- Проверка работоспособности (HEALTHCHECK в Dockerfile, healthcheck в compose.yaml) — команда, которую Docker периодически выполняет внутри контейнера. Код выхода 0 — проверка успешна, любой другой код — неудачна. Команда в виде строки выполняется через /bin/sh -c, команда в виде JSON-массива — напрямую.
- Значения по умолчанию: interval 30s, timeout 30s, retries 3, start_period 0s. Первая проверка выполняется через interval после запуска контейнера, затем — каждые interval.
- Статус: после запуска — (health: starting); успешная проверка сразу даёт (healthy) (в том числе после unhealthy); retries неудачных проверок подряд дают (unhealthy). В течение start_period проверки идут каждые 5 с, неудачи не считаются, а успешная проверка сразу даёт
  (healthy).
- Политика перезапуска (restart policy): on-failure — Docker запускает контейнер заново, если его процесс завершился с ненулевым кодом выхода; always — после любого завершения процесса. Задержка между повторными запусками растёт (от долей секунды до минуты); пока контейнер ждёт повторного запуска, его статус Restarting. Контейнер, остановленный командой stop, заново не запускается.
- Имя проекта Compose по умолчанию — имя каталога, где лежит compose.yaml; контейнеры называются <проект>-<сервис>-1. Другие контейнеры сети находят контейнер по имени сервиса.
- Приложения во фрагментах останавливаются командой stop около 10 секунд; код выхода после stop (Exited (…)) указывать не нужно.
